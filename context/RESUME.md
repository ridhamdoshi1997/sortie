- **New this session:** InsForge's documented REST API (OpenAPI spec, `npx @insforge/cli metadata`, the packaged skill docs) doesn't cover everything the platform can actually do — there is no documented endpoint to delete a user account, but the CLI's own npm package source (downloadable via `npm view @insforge/cli` → tarball URL, or `gh api search/code` against `InsForge/InsForge` on GitHub) reveals real, working admin endpoints like `POST /api/database/advance/rawsql` / `/rawsql/unrestricted` (raw SQL, same admin `INSFORGE_API_KEY` this project already uses) and `PUT /api/auth/smtp-config` (the real way to set SMTP credentials including password — the `config apply`/`insforge.toml` flow has no password field at all). When the packaged docs don't have something, check the CLI's own source before assuming it's not possible.
- **New this session:** the raw-SQL admin endpoint (`/api/database/advance/rawsql/unrestricted`) rejects explicit `BEGIN`/`COMMIT` statements ("Transaction control statements are not allowed") — but a plain multi-statement semicolon-separated string sent in one call IS atomic anyway, because Postgres's simple-query protocol wraps multiple statements with no explicit transaction control in an implicit transaction on its own. Confirmed live both ways: the happy path deletes everything, and a deliberately-broken statement appended after a valid one rolled the valid one back too.
- **New this session:** a `useSearchParams()`-driven Client Component mounted in the root layout (`app/layout.tsx`), even behind a `<Suspense>` boundary, can end up served as genuinely unhydrated static HTML on a cold load when the query param is already present in the URL — no console error, just a component that never runs its effects (checked by looking for React fiber keys directly on the DOM node: `Object.keys(el).some(k => k.startsWith('__react'))`). The root layout also wraps fully static pages (the marketing homepage), which is suspected to be why. Fix: `next/dynamic(..., { ssr: false })` via a small Client Component wrapper (`next/dynamic` with `ssr:false` can't be called directly inside a Server Component). See `components/settings/SettingsModalLoader.tsx`'s comment for the full story — read it before mounting anything else `useSearchParams()`-driven at the root-layout level.
- **New this session:** `revalidatePath(path)` only invalidates the *exact* path given — it does NOT invalidate a dynamic subroute. A server action called from `/resume/[id]` that only did `revalidatePath("/resume")` left that détail page serving a stale cached render indefinitely, even though the underlying data had genuinely changed (confirmed via direct `db query`, not assumption). Any action reachable from a dynamic route needs to revalidate that route's *actual* rendered path too (e.g. `` `/resume/${id}` ``), not just its parent list page. Also add `export const dynamic = "force-dynamic"` to any authenticated, frequently-mutated page — `app/profile/page.tsx` already had this, the newer résumé pages didn't and it was a contributing factor.
- **New this session:** Gemini's own JSON extraction isn't perfectly consistent on casing/formatting run-to-run — the exact same underlying PDF produced `company: "Wizcraft"` on one extraction and `company: "wizcraft"` on a later one. Any dedup/merge key built from AI-extracted string fields needs to be case- and whitespace-normalized (`.trim().toLowerCase()`) before comparing — a case-sensitive key silently treated these as two different companies and created a duplicate profile entry instead of recognizing an existing one.
- **New this session:** an *additive-only* merge (never overwrite existing data, only add what's missing) sounds safe but has a real failure mode — once an entry exists at all, later syncs with much better data silently skip it forever, and there's no visible sign anything is wrong. This is currently `syncResumeToProfile`'s behavior and is the reason old, low-quality profile data survived several résumé syncs undetected this session. Worth designing a real "upgrade if better" path before this bites again, not just documenting around it — see Steps to reorient above.
- **New this session:** the InsForge CLI's raw-SQL endpoint (`db query`) rejected a legitimate multi-line JSONB `UPDATE` using Postgres `$$...$$` dollar-quoting as "could not be parsed and was rejected for security reasons" — not every valid SQL pattern gets through its security filter. When that happens, drop to the `@insforge/sdk`'s `createAdminClient({ baseUrl, apiKey })` (same `NEXT_PUBLIC_INSFORGE_URL`/`INSFORGE_API_KEY` env vars) and use its normal `.database.from(table).update(...)` REST path instead — it isn't subject to the same raw-SQL filter. Must be run as an ESM script (`.mjs`, `import` not `require`) from inside the project directory (`node --env-file=.env script.mjs`) — `@insforge/sdk` has package-exports that break plain CommonJS `require()` resolution, and `NODE_PATH` tricks for a script sitting outside the project don't help ESM's resolver the way they help CJS.
- **New this session, useful for testing:** `lib/usage.ts`'s `checkAndConsumeUsage` fully bypasses the daily cap (and never writes a `usage_daily` row at all) for any email on the `ADMIN_EMAILS` env var allowlist — confirmed live via `usage_daily` query returning zero rows despite real successful calls. If a usage-capped feature seems to "just keep working" during testing with the project's own dev account, that's why — it says nothing about whether the cap logic itself is correct for a real non-admin user.
